# Security scanning & SIEM false positives

Generalized, reusable lessons on SIEM false positives and web frontend exposure scanning.

### MISP/Wazuh "IOC match" on the empty-file hash is a false positive
**Symptom:** A high-severity SIEM alert `MISP IOC match (to_ids): <hash> [hash] event <N> …`, level 14, triggered by File Integrity Monitoring (syscheck) on a node — firing on dozens of OS files.
**Cause:** Three layers, all benign: (1) the IOC value is the **empty/zero-byte file hash** (`d41d8cd98f00b204e9800998ecf8427e` md5 / `da39a3ee…` sha1 / `e3b0c442…` sha256); (2) the MISP event stored its malware-sample hashes **all as the empty-file hash** (defanged/0-byte attachments, `to_ids=1`); (3) FIM reports the empty-file hash for **symlinks** and empty/mid-create files, so every OS symlink (`/usr/bin/xz*`, `/etc/ssl/certs/*.pem` & `*.0`, `/etc/localtime`, systemd `*.wants/*.mount`) matches.
**Fix:** Triage first — compare `data.misp.value` to the three empty-file hashes above; if it matches, it's a false positive. Then pull the triggering paths from the alert archive (all OS symlinks/system files = benign) rather than guessing. Suppress with a local SIEM rule that drops the IOC-match rule to level 0 when the matched value is a known empty/benign hash (fleet-wide, reversible; needs a ruleset reload). Verify with the SIEM's log-test tool (empty hash → level 0, real hash → still fires).
**Note:** Warninglists alone won't fix it — MISP doesn't reliably strip the hash sub-part of composite `malware-sample`/`filename|hash` attributes even with `enforceWarninglist:True`. A real, attacker-plausible path with a **non-empty** matching hash → escalate to incident response.

### Dev web server exposed in production — fingerprint, then confirm with safe file-read
**Symptom:** A production web frontend is actually serving a bundler **dev server** (hot-reload), exposing source and config and, on vulnerable versions, arbitrary file read.
**Cause:** A static SPA was deployed as a live `vite`/webpack dev server instead of a pinned static image; dev-server endpoints (`/@vite/client`, `/sockjs-node/info`, `/_next/webpack-hmr`) are reachable and return a dev body ≠ the SPA `/` fallback. Vulnerable Vite versions add file-read CVEs (CVE-2025-30208/-31125/-31486/-32395/-46909; fixed ≥ 5.4.19 / ≥ 6.3.4).
**Fix:** Detect read-only: enumerate ingress hosts → fingerprint the dev-server endpoints (body ≠ `/` fallback = a live dev server) → confirm with **active-but-safe** file-read on the app's **own benign files only** (`vite.config`/`package.json`/`src/main` via `?import&raw??`/`?raw??`) — **never** `/etc`, `/.env`, `/.git`, or secrets. Add kubectl posture (run command, CPU cap, secret mounts, NetworkPolicy presence). Real fix: pin a static image (no `vite` cmd), add a NetworkPolicy.
**Note:** After remediation, rotate any secrets that were readable (`.env`, `.git/config`, environ) during the exposure window. Keep the scanner read-only by construction (it runs via `bash` and so bypasses any kubectl guard — never add a mutating verb).

### Weak CSP / missing security headers — find the emitting layer before hardening
**Symptom:** A scanner flags a weak `Content-Security-Policy` (`'unsafe-inline'`/`'unsafe-eval'`, broad wildcards) on a web app. You must say definitively which layer emits it and remediate without breaking the app.
**Cause:** The CSP can come from the per-ingress annotation (`configuration-snippet`/`server-snippet` `more_set_headers`, or `add-headers` → a ConfigMap), the controller-wide ConfigMap (applies to every ingress), the app itself, or a CDN/WAF override in front — and the safe fix (nonce vs. hash) depends on whether the app is static or server-rendered.
**Fix:** Locate the ingress for the host; check the per-ingress annotation and the controller-wide ConfigMap. Diff the **live wire header** against the ingress annotation CSP — identical ⇒ CDN passthrough, whole fix is in-cluster; different ⇒ the delta is a CDN edit (lives outside kubectl). Determine static vs. SSR (`curl … | sha256sum` twice — identical ⇒ static ⇒ nonces N/A ⇒ use SHA-256 hashes or externalize inline scripts). Remediate **`Content-Security-Policy-Report-Only` first** (tightened policy alongside the enforced one) across a full QA pass of every route, then promote to enforced.
**Note:** If the app is Helm-managed, a live annotation edit is reverted on the next `helm upgrade` — the durable fix belongs in the chart. An authenticated/deep route may use `script-src` origins a landing page never loads — don't prune an allowlisted origin without per-route confirmation.
