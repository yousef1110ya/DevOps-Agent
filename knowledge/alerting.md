# Alertmanager & alert hygiene

Generalized, reusable lessons for alert floods, blind spots, and false positives in Prometheus/Alertmanager pipelines.

### Alertmanager→Discord silently drops entire alert groups over 4096 chars
**Symptom:** You get *some* alerts but miss others — small alert groups (1–2 alerts) deliver fine, large bursts vanish. The notify-failure counter logs `reason=clientError` (a 4xx), easy to misread as a revoked/invalid webhook.
**Cause:** Alertmanager delivering to Discord via a Slack-compatible receiver (`slack_configs`, api_url ending `/slack`) renders one message per group; when it exceeds **Discord's 4096-char field limit** Discord returns **HTTP 400** `{"description":["Must be 4096 or fewer in length."]}`. Alertmanager treats 400 as unrecoverable → **no retry → the whole group is dropped**. The webhook is fine. With `group_by: [<namespace>]`, any namespace with many simultaneous firing alerts produces an oversized batch that is dropped.
**Fix:** De-group so each alert is its own message — set the route's `group_by` to `["..."]` (the literal ellipsis = every alert its own group). On a prometheus-operator AlertmanagerConfig CR: `kubectl patch alertmanagerconfig <name> -n <ns> --type=merge -p '{"spec":{"route":{"groupBy":["..."]}}}'`. Verify in the generated config. Diagnose via AM logs: `msg="Notify for alerts failed" … status code 400 … Must be 4096 or fewer`.
**Note:** Full de-grouping = N alerts → N messages; Discord may **429** some, but 429 **is** retried (unlike 400) so they still arrive, throttled. Compromise with `group_by: [alertname]` and/or truncate the `.text` template to < ~3900 chars. **Blind spot:** a failing alert channel is itself un-alerted — add an alert on `rate(alertmanager_notifications_failed_total[10m]) > 0` to a second, independent channel.

### Large alert count = false control-plane scrape alerts, not an outage
**Symptom:** A cluster shows a "large number of alerts" — `etcdInsufficientMembers (0)`, `etcdMembersDown`, `KubeSchedulerDown`, `KubeControllerManagerDown`, `KubeProxyDown`, `TargetDown` — firing continuously for weeks/months.
**Cause:** Prometheus can't scrape the control-plane metrics endpoints (etcd, kube-scheduler, kube-controller-manager, kube-proxy — the classic kubeadm `127.0.0.1` bind), so it scrapes 0 members and fires a permanent cluster of false criticals. (The apiserver responding at all proves etcd has members — impossible with the "0 members" alert being real.)
**Fix:** Verify the named pods are `1/1 Running` with live endpoints (`get pods -n kube-system`), then repair/relax the control-plane ServiceMonitors or silence the stock HA rules. Fast read-only alert pull: `kubectl --context <context> get --raw "/api/v1/namespaces/<mon-ns>/services/<alertmanager-svc>:9093/proxy/api/v2/alerts?active=true&silenced=false&inhibited=false"`.
**Note:** On many clusters these route to a `null` blackhole receiver — they clog the dashboard but never page, which means **real problems also go un-alerted** (e.g. a 10-day-dead backup firing nothing). Other recurring noise: backup-job alerts (`KubeJobFailed`/`KubeContainerWaiting`/`KubeJobNotCompleted`).

### Stock alerts never reach the channel — `alertmanagerConfigMatcherStrategy` defaults to `OnNamespace`
**Symptom:** A cluster has a wired Discord/Slack receiver and a default route to it, yet only a handful of custom alerts ever page; every stock kube-prometheus alert falls into the base `receiver: "null"` blackhole.
**Cause:** The Prometheus-Operator's `alertmanagerConfigMatcherStrategy` is unset → defaults to **`OnNamespace`**, which force-injects `namespace="<mon-ns>"` onto the custom route. Only alerts that hard-code `labels.namespace=<mon-ns>` match and page; every stock alert keeps its real namespace, misses the gate, and hits the base default `"null"`.
**Fix (two changes):** (1) `kubectl patch alertmanager <cr> -n <ns> --type=merge -p '{"spec":{"alertmanagerConfigMatcherStrategy":{"type":"None"}}}'`; (2) rewrite the AMC route to default everything → the real receiver, and add a `blackhole` receiver with child routes dropping **only proven noise** (Watchdog/InfoInhibitor; the control-plane scrape criticals incl. TargetDown; ns=default backup-cronjob `KubeJobNotCompleted`/`KubeContainerWaiting`). Bake `matcherStrategy: {type: None}` + blackhole routing into the install template so new clusters are born correct.
**Note:** A healthy pipeline continuously delivers the always-firing `Watchdog` alert — use its presence as the end-to-end heartbeat test.

### "Cluster never sent an alert" = alerting was never wired (default `"null"` receiver)
**Symptom:** A cluster reportedly never sent an alert "since it was created." Two tempting wrong conclusions: "it's just healthy" and "the webhook points at the wrong channel."
**Cause:** The usual real cause is a running-but-default Alertmanager that blackholes everything — the stock chart placeholder has `- name: "null"` as the only receiver and `route.receiver: "null"`. There is nothing to test and nothing was ever sent.
**Fix:** Confirm the stack is actually running (grep **all** namespaces — the `monitoring` ns can be empty while the stack lives elsewhere). Confirm rules exist (Watchdog in `*-general.rules` proves alerts are generated). Decode the effective config (operator merges secret `alertmanager-<name>` → `…-generated`) **to a file, not chat**, and look for the `"null"`-only receiver. Then add a real receiver + point the default route at it (mutating — owner approval).
**Note:** If there's no real receiver, you **cannot** send a "hello" test — report that; never invent a webhook URL. Admission-controller TLS secrets are named `*-webhook-*` (cert-manager, cnpg, emqx operator) — those are **not** alerting webhooks; ignore them. Native `discord_configs` needs Alertmanager v0.25+; older versions need a webhook bridge.

### `KubePersistentVolumeFillingUp` across many PVCs on hostpath = one shared disk, not N problems
**Symptom:** A flood of `KubePersistentVolumeFillingUp` (warning) across many/all PVCs in unrelated namespaces at once, all with near-identical "% available."
**Cause:** On an OpenEBS-hostpath (or any shared-node-disk) cluster, every PVC shares the node's single filesystem with no per-PVC quota, so `kubelet_volume_stats_available_bytes / …capacity_bytes` echoes the **node filesystem free %** for every PVC. A PVC can't fill independently — it grows until the node disk fills.
**Fix:** Prove it with `kubelet_volume_stats_available_bytes/…capacity_bytes*100` per PVC — values collapse into a handful of identical numbers that **group by node, not by app** (a Postgres, a MinIO drive, a Loki vol on the same node all report the same %). Silence/drop `KubePersistentVolumeFillingUp` on hostpath clusters; keep the node-level **High Disk usage** (critical) alert — that one is the only real signal.

### A chronic latency alert can be a protocol artifact, not real latency
**Symptom:** A `LatencyAlert` (e.g. ">10s on path /") fires 24/7, uncorrelated with node load; meanwhile the *actual* user-facing timeouts it's blamed for keep happening unalerted.
**Cause:** The reverse proxy records long-lived connections (WebSocket/SignalR upgrades = **HTTP 101**, SSE, gRPC streams) as ">10s slow requests" — a 101 session is "slow" by definition. The real problem (e.g. a 5s client timeout hitting a single DB replica at peak → HTTP 499 aborts *below* the 10s threshold) is a different signal the alert never catches.
**Fix:** Exclude the WebSocket/streaming path from the latency rule; alert instead on the **499 rate** and POST p95/p99 for the real request path. When chasing "slowness," pull the 499 rate by hour-of-day and backend CPU/throttle at peak rather than the latency alert.
**Note:** Verify the artifact by correlating "requests > Ns" count against status-101 count — if they track, it's the long-lived-connection artifact.
